# Especificação: Fluxo Síncrono do Drift Agent

> Responsável: autor principal do fluxo. Complementa
> `8. especificacao-drift-agent-cifar-corrompido.md`.

---

## 1. Objetivo

Simplificar a implementação atual de drift e entregar um experimento síncrono
de ponta a ponta:

```text
treino limpo → monitoramento corrompido → detecção local →
gatilho coletivo → 5 rounds de retreino → downtime
```

O experimento compara o agente contra uma baseline idêntica sem retreino.

---

## 2. Responsabilidades

- manter somente UDD clássico (MC Dropout + entropia + ADWIN);
- simplificar/remover do caminho principal detectores alternativos, UI e fluxos
  assíncronos de drift;
- implementar um único ciclo de drift e, no máximo, um retreino;
- executar cinco rounds síncronos adicionais com todos os clientes quando o
  gatilho coletivo ocorrer;
- executar e registrar a baseline sem retreino;
- registrar métricas, eventos e downtime;
- testar o fluxo integrado.

Não é responsabilidade desta especificação implementar transformações visuais
ou calibrar severidades. Elas são consumidas pela interface definida no
documento de corrupções.

---

## 3. Fluxo Experimental

1. Distribuir CIFAR-10 limpo, com todas as classes, entre os clientes.
2. Executar o treinamento federado síncrono inicial.
3. Avaliar e registrar a acurácia no teste limpo.
4. Aplicar a corrupção configurada aos batches de produção e aos dados de
   treino destinados ao eventual retreino.
5. Durante a produção, passar apenas `x` corrompido ao detector de cada
   cliente. Não usar rótulos para decidir drift.
6. Agregar os flags por meio da política coletiva existente ou sua versão
   simplificada.
7. No primeiro gatilho:
   - registrar `retrain_decision` com tempo virtual;
   - trocar os datasets dos clientes para a versão corrompida;
   - executar cinco rounds síncronos com todos os clientes;
   - não permitir novo retreino na mesma execução.
8. Avaliar no teste corrompido antes do drift, durante o monitoramento, após
   cada round de retreino e ao final.
9. Computar e gravar downtime.

---

## 4. Simplificação Necessária

O caminho principal tem uma única configuração de detector: UDD. Não há
detector alternativo no repositório nem na interface de linha de comando.

O experimento do agente deve usar apenas o servidor síncrono. O servidor e os
experimentos assíncronos existentes não precisam ser alterados nem removidos;
apenas ficam fora deste novo fluxo.

`Orchestrator` genérico e a lógica do smoke experiment não podem divergir. O
responsável deve escolher uma única fonte de verdade para detector, política e
registro de eventos, evitando duplicação de estado.

---

## 5. Integração com Corrupções

Consumir uma interface equivalente a:

```python
corrupted_x = apply_corruption(
    x,
    kind="gaussian_noise",
    severity=3,
    seed=42,
)
```

O fluxo não deve conhecer parâmetros internos de cada corrupção. Ele recebe
`kind`, `severity` e `seed`, preserva os rótulos originais e usa a mesma
configuração para treino, produção e avaliação corrompidos.

---

## 6. Saída Esperada

Cada execução deve persistir, em formato compatível com os JSONs existentes:

- nome da corrupção, severidade, seed e parâmetros do detector;
- histórico de acurácia corrompida, com tempo virtual;
- histórico de acurácia limpa final;
- `drift_events`;
- uma lista de `retrain_decisions`;
- eventos ou marcadores dos cinco rounds de retreino;
- `downtime_accumulated` para `tau = 0,50`;
- identificação clara de baseline versus agente.

---

## 7. Testes de Fluxo

Cobrir, no mínimo:

1. um evento de drift pode gerar exatamente uma decisão de retreino;
2. a decisão executa exatamente cinco rounds adicionais;
3. a baseline não executa retreino;
4. o JSON contém tempo virtual e os campos necessários para downtime;
5. o downtime é calculado sobre a acurácia corrompida;
6. o modo `train/eval` dos modelos é restaurado após inferências do detector.

Testes podem usar modelo/detector simulado para evitar um treino completo de
CIFAR-10. Um smoke test pequeno valida a integração com dados reais.

---

## 8. Critério de Conclusão

Está concluído quando uma execução reproduzível gera os dois cenários
(`baseline` e `agente`) para uma corrupção configurada, o agente realiza no
máximo um retreino de cinco rounds e os JSONs permitem calcular e comparar o
downtime.
