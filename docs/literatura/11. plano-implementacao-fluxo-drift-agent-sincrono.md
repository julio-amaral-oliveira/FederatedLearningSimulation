# Fluxo Síncrono do Drift Agent — Plano de Implementação

> **Para trabalhadores agentic:** SUB-SKILL OBRIGATÓRIA: use `subagent-driven-development` (recomendado) ou `executing-plans` para implementar este plano tarefa a tarefa. As etapas usam checkboxes para acompanhamento.

**Objetivo:** Entregar o experimento síncrono “treino limpo → monitoramento corrompido → UDD → um retreino de cinco rounds → downtime”, comparável a uma baseline sem retreino.

**Arquitetura:** O `Server` síncrono passa a oferecer um round incremental que preserva relógio virtual, RNG e contador de rounds. Um `DriftMonitor` é a única fonte de verdade para um ADWIN por cliente, uma janela de ticks e eventos temporais; o controlador do experimento é o único responsável por iniciar o retreino. Antes do drift, todos os ADWINs recebem um warm-up limpo. A série usada para downtime contém exclusivamente avaliações do teste corrompido, enquanto as avaliações limpas ficam separadas.

**Tecnologias:** Python 3, PyTorch, NumPy, servidor FL síncrono existente, `unittest`.

## Restrições globais

- Escopo somente síncrono; não alterar o comportamento dos servidores assíncronos.
- Manter apenas UDD: MC Dropout, entropia de Shannon e ADWIN.
- O detector recebe somente `x`; nenhum rótulo é aceito por sua interface.
- O retreino usa todos os clientes e executa exatamente `retrain_rounds=5` por padrão, uma única vez por execução.
- `tau=0.50` significa indisponível apenas quando `accuracy < tau`; igualdade significa disponível.
- Tempo virtual deve ser monotonicamente não decrescente; baseline e agente usam o mesmo horizonte virtual configurado.
- A interface de corrupções do colega é `apply_corruption(x, kind, severity, seed=None) -> torch.Tensor`; este plano não implementa a transformação.
- A configuração de referência usa `num_clients=10`, pois `ceil(0.30 * 10) = 3`; com quatro clientes, um limiar de 30% exigiria dois flags (50%).
- O monitor recebe pelo menos `warmup_ticks=20` ticks limpos por cliente antes do drift, pois o ADWIN atual não testa janelas com menos de 20 observações.
- Preservar alterações não relacionadas já existentes no worktree.

```python
def run_one_round(self, *, record_default_metrics: bool = False) -> dict:
    round_index = self.next_round_index
    weights = get_model_weights(self.global_model)
    client_weights, client_sizes, duration = self.train_clients(round_index, weights)
    started_time = self.virtual_time
    self.virtual_time += duration
    aggregated = bool(client_weights)
    self.aggregate_round(client_weights, client_sizes, round_index,
                         should_record_metrics=record_default_metrics)
    self.next_round_index += 1
    return {
        "round": self.next_round_index,
        "started_time": started_time,
        "completed_time": self.virtual_time,
        "aggregated": aggregated,
    }


def run_rounds(self, num_rounds: int, *, record_default_metrics: bool = False) -> list[dict]:
    if num_rounds < 1:
        raise ValueError("num_rounds must be at least 1")
    return [self.run_one_round(record_default_metrics=record_default_metrics)
            for _ in range(num_rounds)]


def evaluate_dataset(self, testing_data):
    previous_data = self.testing_data
    was_training = self.global_model.training
    try:
        self.testing_data = testing_data
        loss, accuracy, _ = self.evaluate()
        return loss, accuracy
    finally:
        self.testing_data = previous_data
        self.global_model.train(was_training)
```

- [ ] **Passo 4: Transformar `Orchestrator` em monitor de uma única responsabilidade.**

Manter `HeuristicPolicy` somente se ela for reescrita para ticks. Criar `DriftMonitor` com uma instância `UDDDetector(model)` por `client_id`, todas referenciando o mesmo `server.global_model`, mas cada uma com seu ADWIN próprio. A janela armazena os últimos `window_ticks` dicionários de flags; a fração é a quantidade de clientes distintos que tiveram ao menos um `True` na janela dividida pela quantidade de clientes observados em cada tick:

```python
def observe_tick(self, batches_by_client, *, virtual_time):
    flags, scores = {}, {}
    for client_id, x_batch in batches_by_client.items():
        flag, score = self._get_or_create_detector(client_id).update(x_batch)
        flags[client_id], scores[client_id] = bool(flag), float(score)

    self._tick_window.append(flags)
    flagged_clients = {
        client_id for tick_flags in self._tick_window
        for client_id, flag in tick_flags.items() if flag
    }
    fraction = len(flagged_clients) / len(flags) if flags else 0.0
    should_retrain = (not self._decision_taken) and fraction >= self.trigger_threshold
    for client_id, flag in flags.items():
        if flag:
            self.drift_events.append({"client_id": client_id, "score": scores[client_id], "time": virtual_time})
    if should_retrain:
        self._decision_taken = True
        self.retrain_decisions.append({"time": virtual_time, "flagged_fraction": fraction})
    return TickOutcome(flags, scores, fraction, should_retrain)
```

Com `record_action=False`, usado apenas na baseline, ele continua registrando eventos de drift e retorna `should_retrain`, mas grava o primeiro gatilho em `counterfactual_triggers`, não em `retrain_decisions`. Remover do novo fluxo `detector_kind` e `acc_threshold` reservado. Não acoplar `DriftMonitor` ao `Server`; o controlador do experimento decide quando chamar cinco vezes `run_one_round()`.

```python
def compute_downtime(entries, acc_threshold, *, end_time):
    sorted_entries = _sort_entries(entries)
    if end_time < 0:
        raise ValueError("end_time must be non-negative")
    if not sorted_entries:
        return 0.0
    if float(sorted_entries[-1]["time"]) > end_time:
        raise ValueError("end_time must not precede the last entry")

    downtime = 0.0
    for previous, current in zip(sorted_entries, sorted_entries[1:]):
        start, finish = float(previous["time"]), float(current["time"])
        if finish < start:
            raise ValueError("entries must be sorted by non-decreasing time")
        if float(previous["accuracy"]) < acc_threshold:
            downtime += finish - start
    last = sorted_entries[-1]
    if float(last["accuracy"]) < acc_threshold:
        downtime += end_time - float(last["time"])
    return float(downtime)
```

```python
def _run_retraining(result, server, clients, corrupted_client_datasets, corrupted_test, rounds):
    for client, dataset in zip(clients, corrupted_client_datasets):
        client.dataset = dataset
        client.reset_optimizer()
    for _ in range(rounds):
```

`run_drift_comparison` executa primeiro o agente e usa o `end_time_seconds` absoluto do agente como horizonte do baseline. Depois do último tick configurado, a baseline continua ticks parciais ou completos até atingir exatamente esse instante, registrando cada avaliação. O agente também continua ticks se necessário até esse horizonte. Assim os dois resultados têm o mesmo período `[production_start_time, end_time_seconds]`; se um retreino terminar após o horizonte mínimo de monitoramento, o tempo extra é contado como indisponibilidade potencial no agente e como tempo ocioso monitorado na baseline.

Antes de executar os dois cenários, criar um snapshot dos pesos do modelo global, dos datasets limpos e do estado aleatório inicial.
